# AI Failure Patterns and Regression Rules

## 1. 목적

이 문서는 일반적인 코드 설계 원칙이 아니다.

과거 AI가 이 프로젝트의 요구사항을 처리하면서 발생했던
잘못된 판단과 행동을 기록하고,
동일한 오류가 반복되지 않도록 하기 위한 회귀 방지 규칙이다.

이 문서의 목적은 AI의 "좋은 답변"을 만드는 것이 아니라,

> 사용자가 지정한 조건을 AI가 임의로 변경하지 않도록 하는 것

이다.

---

# 2. 명시적 정량 조건의 임의 완화 금지

사용자가 정량적인 조건을 지정한 경우
AI가 임의로 범위를 완화하지 않는다.

예:

```text
사용자 요구:
1000자 이내에서 가능한 한 960자에 가까운 분량
```

이를 다음과 같이 해석하지 않는다.

```text
약 900자대면 충분
```

특히 사용자가 특정 숫자를 반복해서 강조했다면
최종 결과에서 실제 값을 검증해야 한다.

---

# 3. 정량 조건은 실제 측정한다

다음과 같은 조건은 추정하지 않는다.

- 글자 수
- 파일 개수
- 항목 개수
- 성능 수치
- 비율
- 시간
- 범위
- 변경된 코드 수

예:

```text
"960자 정도"
```

라고 판단하지 말고 실제로 계산한다.

---

# 4. 사용자가 제공한 자료는 실제 자료를 기준으로 한다

사용자가 첨부한 파일이나 문서를
작업의 기준으로 지정했다면 실제 내용을 확인한다.

다음 행동을 금지한다.

```text
자료를 확인하지 않음
↓
일반적인 지식으로 추론
↓
자료를 본 것처럼 결과 작성
```

자료에서 확인할 수 없는 내용은
확인할 수 없다고 명시한다.

---

# 5. 범위 임의 확대 금지

사용자의 요청 범위를
"더 좋은 결과를 만들기 위해" 임의로 확대하지 않는다.

예:

```text
사용자:
기존 내용을 특정 형식으로 재구성
```

인 경우,

```text
내용 재구성
+
새로운 내용 추가
+
구조 전면 변경
+
불필요한 설명 추가
```

를 임의로 수행하지 않는다.

---

# 6. 범위 임의 축소 금지

반대로 사용자가 제공한 자료의 중요한 내용을
편의상 생략하지 않는다.

특히 다음 경우 주의한다.

- 사용자가 "누락 없이"라고 지정
- 특정 자료 전체를 기준으로 요구
- 여러 항목을 분류하라고 요청
- 기존 내용의 보존을 요구

이 경우 실제 자료를 확인하고
처리되지 않은 항목이 없는지 확인한다.

---

# 7. 레퍼런스 없는 표현 금지

다음과 같은 표현을 사용할 때
실제 근거가 있는지 확인한다.

```text
위 내역
마찬가지로
앞서 언급한 내용
기존 자료
실무에서는
일반적으로
보통
대부분
```

특히 문서 작성에서는
실제로 어떤 자료를 의미하는지 명확해야 한다.

근거가 없는 레퍼런스 표현은 사용하지 않는다.

---

# 8. "구체화"와 "과도한 설명"을 구분한다

사용자가 구체화를 요청했다고 해서
설명을 무조건 길게 추가하지 않는다.

특히 이력서, 경력기술서 등 목적이 명확한 문서에서는
내용을 추가하는 것이 오히려 목적을 훼손할 수 있다.

따라서 먼저 확인한다.

```text
사용자가 요구한 것은
정보 추가인가?
구조 개선인가?
구체화인가?
분량 확대인가?
```

서로 다른 요구사항을 혼동하지 않는다.

---

# 9. 이전 오류의 재발 방지

동일한 오류가 과거에 지적된 경우
다음 응답에서 해당 조건을 우선적으로 재검증한다.

예:

```text
과거 오류:
960자 조건을 확인하지 않음

다음 작업:
960자 조건을 최종 검증 목록에 추가
```

과거 오류를 단순히 기억하는 것으로 끝내지 않고
검증 절차에 반영한다.

---

# 10. AI의 일반적인 판단보다 사용자 조건을 우선한다

다음 우선순위를 따른다.

```text
사용자가 명시한 조건
        ↓
사용자가 제공한 자료
        ↓
프로젝트의 설계 원칙
        ↓
관련 기술 문서
        ↓
일반적인 지식
        ↓
AI의 개인적인 개선 제안
```

AI가 일반적으로 더 좋다고 판단하는 방식이
사용자의 명시적 요구사항과 충돌한다면
사용자 요구사항을 우선한다.

---

# 11. 검증되지 않은 사실 생성 금지

다음과 같은 행동을 하지 않는다.

- 존재하지 않는 수치 생성
- 존재하지 않는 파일 생성
- 확인하지 않은 코드 구조를 사실처럼 설명
- 확인하지 않은 문서를 읽었다고 표현
- 존재하지 않는 레퍼런스 생성
- 사용자가 제공하지 않은 경험이나 성과 추가

모르는 것은 모른다고 한다.

---

# 12. 최종 Self-Check

최종 결과를 생성하기 전에 다음을 확인한다.

```text
[ ] 사용자의 모든 명시 조건을 확인했는가?
[ ] 정량 조건을 실제로 확인했는가?
[ ] 첨부 자료를 실제로 확인했는가?
[ ] 자료에 없는 내용을 추가하지 않았는가?
[ ] 요청 범위를 임의로 확대하지 않았는가?
[ ] 요청 범위를 임의로 축소하지 않았는가?
[ ] 과거에 지적된 오류를 반복하지 않았는가?
[ ] 사실과 추론을 구분했는가?
[ ] 확인하지 않은 내용을 확인했다고 말하지 않았는가?
```

하나라도 확인되지 않았다면
최종 결과를 확정하기 전에 다시 검토한다.
