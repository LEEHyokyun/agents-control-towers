# Engineering Philosophy

## 1. Core Philosophy

> 목적에 맞는 기술, 관계에 의한 기술

기술은 그 자체가 목적이 아니다.

프레임워크, 라이브러리, 디자인 패턴, 아키텍처, 인프라를 사용하는 이유는
현재 시스템이 해결해야 하는 문제와 그 문제를 둘러싼 관계에 의해 결정한다.

따라서 다음과 같은 판단을 기본적으로 경계한다.

- 최신 기술이기 때문에 사용
- 유명한 패턴이기 때문에 사용
- 확장성을 위해 무조건 추상화
- 테스트를 위해 무조건 인터페이스 생성
- Clean Architecture이기 때문에 계층 추가
- DDD이기 때문에 Domain 객체 생성
- MSA이기 때문에 서비스 분리
- Redis/Kafka 등의 인프라를 사용하기 위해 문제를 재정의

기술 선택의 근거는 반드시 문제와 연결되어야 한다.

---

# 2. 문제 → 원인 → 해결책

설계는 다음 순서를 따른다.

```text
문제
 ↓
현상
 ↓
원인
 ↓
제약조건
 ↓
해결해야 할 책임
 ↓
가능한 해결책
 ↓
비용과 부작용
 ↓
기술/구조 선택
```

해결책을 먼저 정하고 문제를 끼워 맞추지 않는다.

예를 들어:

```text
Redis를 사용한다.
```

가 먼저 나오면 안 된다.

대신:

```text
조회 부하가 특정 DB에 집중된다.
↓
DB가 병목이다.
↓
데이터의 변경 빈도와 정합성 요구사항을 확인한다.
↓
캐시가 적합한지 판단한다.
↓
캐시 전략을 결정한다.
↓
그중 Redis가 필요한지 판단한다.
```

와 같이 문제에서 기술로 이동한다.

# 3. 기술 선택 기준

기술 또는 구조를 선택할 때 다음 요소를 고려한다.

### 목적

무엇을 해결하기 위해 필요한가?

### 관계

기존 컴포넌트와 어떤 관계를 형성하는가?

### 변경 가능성

어떤 부분의 변경을 독립시켜야 하는가?

### 복잡성

추가된 구조가 전체 시스템의 복잡성을 얼마나 증가시키는가?

### 운영 비용

배포, 모니터링, 장애 대응, 데이터 관리 등의 비용은 무엇인가?

### 실패 방식

해당 기술 또는 구조가 실패하면 시스템은 어떻게 동작하는가?

### 정합성

데이터 정합성 요구사항과 충돌하지 않는가?

### 성능

성능 개선이 실제 병목과 연결되는가?

# 4. 단순성

단순한 구조는 낮은 수준의 설계가 아니다.

현재 요구사항을 충족하는 가장 단순한 구조가 있다면
불필요하게 복잡한 구조로 변경하지 않는다.

```text
단순한 구현
<
복잡한 구현
```

이 아니라,

```text
문제를 충분히 해결하는가?
+
변경 가능성을 적절히 수용하는가?
+
복잡성 비용이 정당한가?
```

를 기준으로 판단한다.

---

# 5. 복잡성의 정당화

추상화, 계층, 패턴, 인프라, 분리 등으로 복잡성이 증가한다면
그 복잡성을 추가할 이유가 존재해야 한다.

예:

```text
Interface 추가
→ 구현체가 여러 개가 될 가능성이 존재
→ 실제 교체 가능성을 확보
→ 의존성 방향 개선
```

이라면 정당화될 수 있다.

반면:

```text
Service
→ ServiceInterface
→ ServiceImpl
```

구조가 단순히 관습이라는 이유로 추가된다면
추상화의 실익을 검토한다.

---

# 6. 시스템 관점

개별 클래스의 아름다움보다
전체 시스템에서의 관계를 중요하게 본다.

검토 대상은 다음과 같다.

- 객체 간 관계
- 계층 간 관계
- 데이터와 코드의 관계
- 동기/비동기 관계
- 트랜잭션 경계
- 캐시와 원본 데이터의 관계
- 메시지와 처리 결과의 관계
- 장애와 복구의 관계
- 외부 시스템과 내부 시스템의 관계

설계는 개별 기술이 아니라
**시스템 내 관계를 어떻게 구성하는가**의 문제다.
