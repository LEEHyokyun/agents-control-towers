# Abstraction Principles

## 1. 추상화의 목적

추상화의 목적은 코드를 어렵게 만드는 것이 아니다.

추상화는 구체적인 구현의 변화가
그 구현을 사용하는 코드에 불필요하게 전파되지 않도록 하는 수단이다.

따라서 추상화가 추가되었을 때 반드시 질문한다.

> 무엇의 변화를 격리하고 있는가?

대답할 수 없다면 추상화의 필요성을 의심한다.

---

# 2. Interface

인터페이스는 존재 자체가 좋은 것이 아니다.

다음과 같은 경우 인터페이스의 필요성을 검토한다.

### 구현 교체

```text
Implementation A
Implementation B
```

처럼 실제로 여러 구현이 존재하거나
교체 가능성이 중요한 경우.

### 정책 분리

구현 방법이 아닌 정책 자체를 분리해야 하는 경우.

### 의존성 역전

상위 정책이 구체적인 인프라 구현에 직접 의존하지 않도록
경계를 형성해야 하는 경우.

### 외부 경계

외부 시스템과 내부 정책 사이에 명확한 계약이 필요한 경우.

---

# 3. One Implementation Interface

다음 구조를 자동으로 좋은 설계라고 판단하지 않는다.

```text
UserService
UserServiceImpl
```

현재 구현체가 하나라는 사실 자체가 문제는 아니다.

판단 기준은 구현체의 개수가 아니라
**추상화가 실제로 어떤 경계를 보호하는가**이다.

---

# 4. Strategy Pattern

Strategy Pattern은 조건문이 존재한다는 이유만으로 적용하지 않는다.

다음 조건을 함께 검토한다.

```text
서로 다른 정책이 존재한다.
+
각 정책의 변경 이유가 다르다.
+
정책 선택이 독립적으로 이루어진다.
+
정책이 추가될 가능성이 실제 문제와 연결된다.
```

예를 들어 단순한 조건문:

```java
if (type == A) {
    ...
} else {
    ...
}
```

만으로 Strategy를 강제하지 않는다.

반대로 정책이 지속적으로 추가되고
각 정책이 독립적으로 변경된다면
Strategy를 검토한다.

---

# 5. Factory

Factory는 객체 생성 과정이 실제로 복잡하거나
생성 정책을 호출자로부터 분리해야 할 때 사용한다.

단순히 `new` 하나를 감추기 위해 Factory를 생성하지 않는다.

---

# 6. Adapter

Adapter는 서로 다른 인터페이스나 모델 사이의 차이를
경계에서 격리하기 위한 수단이다.

외부 시스템의 데이터 모델이 내부 Domain 모델로
직접 침투하는 경우 Adapter가 유효할 수 있다.

---

# 7. Decorator

Decorator는 기존 객체의 계약을 유지하면서
행동을 조합하거나 추가해야 하는 경우 검토한다.

단순한 메서드 호출 하나를 감싸기 위해
무조건 Decorator를 생성하지 않는다.

---

# 8. Pattern Overengineering

다음 구조를 발견하면 먼저 의심한다.

```text
Interface
    ↓
Abstract Class
    ↓
Factory
    ↓
Strategy
    ↓
Concrete Implementation
```

구조가 많다는 사실만으로 잘못된 것은 아니다.

그러나 각 계층이 어떤 문제를 해결하는지
각각 설명할 수 있어야 한다.

설명할 수 없는 구조는 제거 가능성을 검토한다.

---

# 9. Abstraction Cost

추상화를 추가하면 다음 비용이 발생할 수 있다.

- 클래스 증가
- 탐색 비용 증가
- 호출 관계 증가
- 디버깅 난이도 증가
- 이해해야 할 개념 증가
- 테스트 대상 증가
- 변경 지점 증가

따라서 추상화의 이익이 비용보다 큰지 판단한다.

---

# 10. 판단 공식

추상화는 다음 질문을 통과해야 한다.

```text
무엇을 숨기는가?
↓
왜 숨겨야 하는가?
↓
어떤 변경을 격리하는가?
↓
실제로 변경 가능성이 존재하는가?
↓
추상화 비용보다 이익이 큰가?
```

하나라도 명확하게 설명하기 어렵다면
추상화하지 않는 선택을 함께 검토한다.
