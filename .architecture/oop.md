# Object-Oriented Design Principles

## 1. 객체의 핵심은 데이터가 아니라 책임이다

객체를 설계할 때 단순히 필드를 기준으로 클래스를 분리하지 않는다.

먼저 질문한다.

> 이 객체는 무엇을 책임지는가?

책임이 명확하면 해당 책임을 수행하는 데 필요한 상태와 행동을 함께 묶는다.

---

# 2. 책임의 응집도

하나의 객체가 서로 관련 없는 여러 책임을 수행한다면 분리를 검토한다.

그러나 메서드가 많다는 이유만으로 분리하지 않는다.

다음 요소를 기준으로 판단한다.

- 변경 이유
- 사용하는 상태
- 사용하는 의존성
- 비즈니스 책임
- 생명주기
- 테스트 경계

서로 같은 이유로 변경되는 기능이라면
하나의 객체에 존재하는 것이 더 자연스러울 수 있다.

---

# 3. 캡슐화

상태를 외부에 무분별하게 노출하지 않는다.

특히 객체가 반드시 유지해야 하는 불변조건이 있다면
그 불변조건을 객체 내부에서 보호한다.

좋은 캡슐화는 단순히 getter/setter를 줄이는 것이 아니다.

> 객체가 자신의 상태가 올바르게 유지되도록 책임지는가?

를 기준으로 판단한다.

---

# 4. 데이터와 행동의 결합

행동이 특정 데이터에 강하게 의존한다면
가능한 한 해당 데이터와 가까운 곳에 책임을 둔다.

예:

```text
Order 상태 변경 규칙
→ Order 내부에서 관리
```

단순히 Service에서 모든 상태 변경을 수행하도록 만들지 않는다.

그러나 모든 비즈니스 로직을 Domain 객체에 넣는 것도 강제하지 않는다.

외부 시스템 호출, 트랜잭션 조정, 여러 객체의 협력 조정 등은
Application/Service 계층의 책임일 수 있다.

---

# 5. 다형성

다형성은 조건문을 제거하기 위한 기술이 아니라
**변경 가능한 정책을 분리하기 위한 수단**으로 본다.

다음과 같은 경우 다형성을 검토할 수 있다.

- 여러 구현체가 실제로 존재한다.
- 구현체가 교체될 가능성이 있다.
- 정책이 독립적으로 변경된다.
- 호출자가 구현 세부사항에 의존하면 안 된다.
- 새로운 정책 추가가 기존 코드를 지속적으로 수정하게 만든다.

단순한 조건문 하나를 제거하기 위해
다수의 클래스를 생성하지 않는다.

---

# 6. 상속

상속은 단순 코드 재사용을 목적으로 사용하지 않는다.

상속 관계를 만들 때는 다음을 확인한다.

- 실제 is-a 관계가 존재하는가
- 부모의 계약을 자식이 자연스럽게 만족하는가
- 부모의 변경이 자식에게 부작용을 주지 않는가
- 상속보다 조합이 더 적절하지 않은가

단순 코드 중복 제거 목적이라면
상속보다 다른 방법을 우선 검토한다.

---

# 7. 객체 분리의 기준

다음과 같은 상황에서는 분리를 검토한다.

```text
변경 이유가 다르다.
의존성이 다르다.
생명주기가 다르다.
테스트 경계가 다르다.
책임의 성격이 다르다.
```

반대로 다음만으로 분리하지 않는다.

```text
메서드가 많다.
클래스가 길다.
책에서 분리하라고 했다.
SOLID를 적용하기 위해 필요하다.
미래에 확장될 수도 있다.
```

---

# 8. OOP 리뷰 질문

코드를 검토할 때 다음 질문을 사용한다.

1. 이 객체의 핵심 책임은 무엇인가?
2. 이 책임과 관계없는 기능이 들어가 있는가?
3. 객체가 자신의 상태를 보호하고 있는가?
4. 다른 객체의 내부 상태를 과도하게 조작하고 있지 않은가?
5. 다형성이 실제 변경 가능성을 해결하는가?
6. 인터페이스가 실제 대체 가능성을 제공하는가?
7. 상속 관계가 실제 의미적 관계인가?
8. 조합으로 더 단순하게 표현할 수 있는가?
9. 객체 분리가 실제 복잡성을 줄이는가?
10. 분리로 인해 오히려 객체 간 결합이 증가하지 않는가?
